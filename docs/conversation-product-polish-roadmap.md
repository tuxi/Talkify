# 对话详情产品化打磨路线

2026-11-18。目标是让新对话、执行过程、结果和继续输入形成连贯的产品体验。以已确认的 macOS 对话详情视觉方案为基础，逐步实施；本文是规划和观察记录，不代表功能已经实现。

## 已确定的后续方向

| 优先级 | 方向 | 体验目标与验收场景 |
| --- | --- | --- |
| P1 | 滚动与流式回复稳定性 | 底部自然跟随；向上阅读即停止跟随；工具展开、图片加载、消息折叠及输入框高度变化时保持阅读锚点；回到最新入口清楚且不遮挡内容。 |
| P1 | 任务执行过程的统一表达 | 一眼知道任务已开始、整体计划、当前动作和是否需要用户介入；执行结束后有明确收尾。 |
| P2 | 长回复阅读节奏 | 多级标题、嵌套列表、表格、引用和代码组合时仍清楚；短回复不过松、长回复不过密；表格与代码在各自区域横向滚动。 |
| P2 | 运行及异常状态 | 思考、工具运行、审批、取消、失败和完成各自清楚；错误优先说明发生了什么及可采取的行动，诊断细节按需查看。 |
| P2 | 附件与正文关系 | 图片、文件、目录混排保持单行横向展示；名称、类型、缩略图与点击反馈统一；少量附件轻巧，多附件不挤压正文。 |
| P2 | 辅助操作可发现性 | 悬停或键盘聚焦可发现复制、时间和更多操作；进入菜单后不消失；复制成功轻量反馈；操作出现不推动正文。 |

具体工具展开机制由工具展示专项负责。此路线主要约定跨组件的层级、位置和状态规则，实施时先核对现有能力，避免重复建设。

## Claude 桌面端实机观察

### 范围与事实

用户已在 Claude Code 新会话输入框准备好 P1-H 独立验收任务，并明确授权发送。已发送，工作目录显示为 chater，新会话自动命名为“P1-H 图像输入独立验收”。界面模型选择显示 deepseek-v4.1-flash / High，权限显示 Auto；本文观察的是 Claude 桌面客户端的交互，不能据此评价 Claude 模型本身的能力或速度。

观察覆盖发送、新会话建立、初始执行说明、任务清单、连续命令摘要、展开/收起执行详情及会话详情面板。后续按用户授权补测了运行中的普通发送、排队、编辑及移除。观察结束时任务仍在运行，尚未看到最终验收结果、任务完成状态或全部清单状态变化。没有停止任务或批准权限扩展。

### 观察与可借鉴的规则

1. **发送是完整的状态转换。** 发送后进入正式会话，长用户消息折叠并显示底部渐隐和 Show more，输入框清空并恢复紧凑单行，主操作变为停止。标题和 sidebar 使用同一个自动生成的任务名。建议把这些状态作为一次一致的提交体验验收，覆盖发送失败保留草稿、成功清空及附件清理。

2. **任务有整体计划，也有眼前动作。** 页面先出现简短执行说明，再出现七项任务清单；当前项和未完成项用不同状态符号表示。这里是模型维护的任务计划，对应 chater 已有的 Tasks，不是建议另加一个计划组件，也不能仅凭外观认定为需要审批的正式 Plan。用户确认 chater 的 Tasks 完成后收起为一行，保留此方向。清单下方以轻量动态标记、动作描述、耗时和展开入口表示当前执行。模型清单依赖真实更新；本次后续观察中，执行说明已推进，但清单仍停留第一项，不能把它当作自动推算的真实进度。

3. **当前清单与最新活动保持关联。** 连续出现新的执行说明后，观察到页面仍只展示一份清单，位于较新的执行说明之后、当前活动之前。它不是固定在视口上的浮层。建议先验证 chater 的现有任务清单和 Session rail 如何分工：若需要在正文展示，应使用当前状态投影，避免每次更新堆积一张历史清单；重新定位时要尊重用户阅读锚点。完成后如何收拢仍待单独观察确认。

4. **历史过程压缩为可理解的摘要。** 一条命令结束后显示过去式说明；后续连续命令在观察中聚合为 Ran 10 commands。当前执行仍保留具体动作描述。这让解释性正文和执行记录保持不同层级。聚合边界、准确计数与展开机制由工具专项落实，不能用视觉摘要抹掉错误或审批。

5. **默认简洁，细节有入口。** 点击已完成的动作摘要，展开 Bash 类型、原始命令、复制入口和独立滚动的输出；再次点击收起。展开历史详情时出现 Scroll to bottom 入口，输入框仍固定在底部。值得借鉴的是信息的渐进展示，具体卡片层数和装饰不必照搬。

6. **执行中仍允许继续组织输入。** 输入框保留，提示 Enter 发送、Command+Enter 排队。已补测两条路径，实测记录与 chater 建议见下节。排队自动消费时机、工具是否被打断等内部语义仍未验证。

7. **环境信息集中按需查看。** 会话顶部有启动环境与目录提示；Session details 入口集中展示 Environment、Context、Connectors、Changes。当前窗口下它呈现为右侧浮动面板。观察到的变更计数只能说明界面展示了仓库状态，不能认定全部由这次任务产生。可借鉴的是摘要与详细信息分层，避免在输入框和正文重复显示同类运行信息。

### 产品判断与实施建议

最有价值的是建立一条稳定的信息顺序：用户交代任务 → 确认已开始 → 整体计划 → 阶段说明与过程摘要 → 当前动作 → 结果或需要用户操作的状态 → 继续输入。

下一次设计建议先聚焦“执行中的任务进度与当前活动”：盘点现有 todo、Session rail、工具摘要和运行状态；用同一份任务的开始、进行、等待、失败和完成五种状态画出位置与信息层级，再决定最小实现范围。任务清单应服务于确有多步骤的任务；简单问答无需额外增加计划卡片。状态依赖服务端明确事件，缺少进度数据时只显示可信的当前活动，不估算百分比、不伪造完成项。

本文未测量该客户端帧率、输入延迟、内存或网络性能；不根据静态截图判断内部渲染策略。

## 运行中发送与排队补测

### 实测结果

- **普通 Enter：** 发送“最终报告请用中文，请继续原验收，无需单独回复”的轻量补充。消息立即出现在正式对话，输入框清空，原执行内容成为上一条 assistant 消息，计划出现 `Plan from before your last message` 标签，随后出现新的运行活动。可以确认是立即进入对话的路径，不能确认服务端立即读取、取消了某个模型请求或中断了当前工具。
- **Command+Enter：** 将“报告末尾单列未通过和未验证项”的另一条格式补充排队。输入框清空，上方出现单行 `1 message queued` 和内容预览；提供 `Send now`、`Edit in composer`、`Remove from queue`。该补充尚未出现在正式消息历史，原活动继续。
- **编辑：** 点击 `Edit in composer` 后，排队条目消失，全文返回输入框，等待重新提交。不能据此判断内部是移除后重建还是原地更新。
- **移除：** 将编辑内容再次排队，再点击 `Remove from queue`，队列条目消失，输入框为空，任务继续。第二条测试消息已移除；只留下第一条中文报告补充作为正式消息。
- **未测：** 自动消费时机、多条 FIFO 顺序、Send now 的内部语义、重启恢复、并发编辑/消费和工具中断。没有为了观察而等待整个独立验收任务结束。

### chater 的建议语义（待设计确认，不代表 Claude 内部实现）

| 用户意图 | 客户端表现 | 服务端约定 |
| --- | --- | --- |
| 立即补充当前任务 | Enter/发送；成功确认后进入对话，可短暂显示“已送达，待处理” | 持久接收补充，在明确的安全检查点交给当前任务；不默认强杀已运行工具；区分已接收与模型已读取。 |
| 当前轮完成后再执行 | Command+Enter/稍后发送；输入框上方一条轻量队列摘要 | 持久队列，当前轮结束后按约定顺序启动下一轮；等待审批不等于完成，不自动越过审批。 |
| 提前处理排队消息 | 队列条目的“立即发送” | 服务端原子地从 queued 转为当前任务补充或下一次处理，具体语义需明确，避免双重消费。 |
| 修改或取消 | 编辑回输入框；移除后立即同步状态 | queued 状态才可修改/撤回；若已被领取，返回真实状态，不假装撤回成功。编辑回输入框与移出队列应有一致的确认机制。 |

第一版外观保持克制：无队列时没有额外条目；有队列时显示数量、简短预览及必要操作，多条再展开。成功确认后清空对应的文字与附件；发送失败保留草稿。立即补充、排队、停止使用不同的明确语义，模型、权限和附件沿用当前输入框能力。

服务端需先定义消息 ID、幂等提交、会话内顺序、queued/claimed/consumed/cancelled/failed 状态及事件回放。提交、编辑、取消、提前发送和消费必须处理并发竞争；断线恢复以服务端状态为准，避免重复发送和 UI 丢队列。模型/权限/附件是在提交时冻结还是执行时解析也需明确定义。Tasks 保留原有计划与完成状态，插入补充不把旧计划标记完成；若需要区分继承计划，可用轻量来源说明。

## 分阶段执行计划

以下是本次观察的执行拆分。阶段 1 已确认，阶段 2 已实现，详见 [阶段 2 记录](designs/conversation-execution-v1/phase-2.md)；后续阶段待推进。[阶段 1 能力清单与五态设计](designs/conversation-execution-v1/phase-1.md) 和 [可切换预览](designs/conversation-execution-v1/index.html) 保留为设计依据。先做 macOS，每阶段形成可单独验收的结果，通过后再提交。源代码盘点不等同于服务端运行验收。

| 阶段 | 独立交付物 | 依赖 |
| --- | --- | --- |
| 1. 现状与交互定稿 | 现有能力清单、信息归属、五种执行状态设计及发送语义表 | 无 |
| 2. Tasks 与当前活动统一 | macOS 执行过程的完整展示与收尾 | 1 |
| 3. 动态布局与滚动稳定 | 任务卡片、工具、图片、输入框变化时的稳定阅读体验 | 2 |
| 4. code-agent 消息处理基础 | 可独立测试的运行中补充与持久队列契约及实现 | 1；建议在 2、3 的体验验收后推进 |
| 5. macOS 最小消息闭环 | 运行中补充、稍后发送、自动消费及断线恢复的端到端体验 | 3、4 |
| 6. 队列管理 | 编辑、移除、立即发送及并发冲突处理 | 5 |
| 7. 产品收尾与整体验收 | 阅读细节、异常表达、辅助操作和性能证据 | 6；相关阅读小项可单独提前交付 |

### 阶段 1：盘点现状，确定一套交互

- 读取 chater、AgentKit 和 code-agent 的相关实现，列出 Tasks、正式 Plan 审批、当前活动、Session rail、发送、后台等待与草稿的已有能力及缺口，先确认复用点。
- 明确信息归属：Tasks 表示模型维护的多步骤清单；活动行表示正在发生的动作；审批条表示等待用户决策；最终回复承载结果。正文和 Session rail 使用同一状态来源，避免冲突或重复主展示。
- 用同一项任务制作开始、进行、等待用户、失败、完成五种状态图。包括无 Tasks 的简单问答、部分完成、旧计划继承、用户手动展开已完成 Tasks。
- 形成运行中发送语义表，分别定义补充当前任务、排队下一轮、停止、当前轮结束条件；区分后台等待、审批等待、成功、失败与取消。Enter/Command+Enter 只是操作入口，最终行为需与现有服务端能力一起确定。
- **验收：** 用户确认信息层级与五种状态；已有能力、待实现能力和未定语义有明确记录。此阶段不改运行逻辑。

### 阶段 2：统一 Tasks、当前活动与结束状态

- 优化已有 Tasks 的表面、间距、状态符号及完成数量；延续“完成后默认收成一行、可再次展开”的行为。没有 Tasks 数据不创建空卡片，部分完成不显示全完成。
- 正文中每个任务范围展示一份当前清单，更新当前状态而非堆积重复清单。确定它与最新执行说明、活动摘要之间的位置；不因移动清单而重建工具内容。
- 当前活动用一处轻量状态表达，复用工具专项提供的摘要。处理运行、等待审批/提问、失败、取消和完成的切换，避免多个等价的 Working/Thinking 标签。
- 新消息进入后保留正确的计划归属；不因为上一段 assistant 消息结束就把整个任务或其清单标记完成。
- **验收：** 同一任务的五种状态均可复现；完成 Tasks 默认一行；简单问答轻巧；等待操作清楚；失败信息仍可查；live 与 replay 状态一致。工具展开内部机制不在本阶段重做。

### 阶段 3：稳定动态布局与滚动

- 检查 Tasks 更新/收起、工具展开、图片加载、用户消息展开、输入框高度变化和队列区域预留的共同影响。
- 底部跟随和历史阅读分开验证：用户离开底部后保持阅读锚点，回到最新入口固定且不遮挡输入框；用户手势优先。
- 记录同一长对话场景的渲染与展开基准，检查流式更新是否保留无关历史 DOM，是否提前挂载大型输出。
- **验收：** 上述变化不把历史读者拉到底部；底部用户能继续看到最新内容；连续快速更新、窗口缩放和会话切换保持正确；性能报告区分测量事实与主观流畅感。

### 阶段 4：先完成 code-agent 消息处理基础

- 阶段 1 已确认存在持久 TurnInput、同会话 scheduler 排队、幂等和有条件恢复入口。先复用并验证这些基础，核对与扩展接口，定义运行中补充的安全处理点及“已接收/已读取”的事件，不以消息气泡出现代替模型已读取。
- 实现持久消息队列与消费规则：消息 ID、幂等键、会话内顺序、领取和消费状态、重启恢复、失败保留及事件回放。明确一个队列项与用户消息、运行轮次的关联。
- 定义当前任务结束时的竞争行为：补充恰好晚到、排队时当前轮恰好结束、用户取消任务、当前轮失败、等待审批及后台作业尚未结束。建议异常或取消后保留队列并暂停自动推进，最终以阶段 1 确认的策略为准。
- 明确模型、权限、工作区、图片/文件引用等执行上下文的绑定时机与资源生命周期；等待中权限或环境变化时不能悄悄扩大执行权限。
- 为客户端提供能力协商和不支持时的明确返回，保证旧客户端、旧服务端可以按既有能力使用。
- **验收：** 服务端测试覆盖正常消费、重复提交、断线重连、重启、失败/取消/审批及边界竞争；同一逻辑消息不会因重试重复启动执行；相关状态可通过事件重建。此时不在产品中暴露尚未接通的队列 UI。

### 阶段 5：接通 macOS 最小发送闭环

- 接入服务端真实确认和读取状态，实现运行中补充及稍后发送；确认成功后才清理本次提交对应的文字与附件，保留提交期间新输入的内容，失败保留可重试草稿。
- 输入框上方显示轻量排队摘要：数量与内容预览；多条可以展开。未支持的管理操作不提前出现，无队列时不占行。
- 接通自动消费与正式消息历史：排队中的内容有明确身份，消费后正确进入历史，原队列项消失；收到新补充时原 Tasks 状态保持可信。
- 断线、重连、切换会话和应用重启后恢复队列；服务端不支持时提供明确兼容行为，不把本地临时列表表现成持久队列。
- **验收：** 用真实 code-agent 跑通“执行中补充 → 读取 → 继续执行”及“两条排队消息 → 按约定消费 → 历史回放”；同时覆盖文字、图片/文件引用、发送失败、提交期间继续输入和重连。先让端到端闭环稳定，再增加管理操作。

### 阶段 6：补齐编辑、移除与立即发送

- 服务端先提供原子修改、取消和提前发送操作，并定义 queued 与 claimed 边界；客户端随后接入。阶段 4 的状态设计需为这些操作保留扩展位置。
- 编辑回输入框时处理已有未发送草稿，不能静默覆盖；只有确认移出队列后才能表现为已撤回，操作失败保留原条目及内容。
- “立即发送”按已确认的语义处理；同时消费或重连时不重复插入。若消息已领取，明确显示已开始处理，避免给出假成功。
- **验收：** 编辑成功/失败、已有草稿、取消与领取竞争、重复点击、提前发送与自动消费竞争、刷新后的状态一致；所有结果以服务端确认为准。
