# Changes 工作台设计草案

状态：设计讨论稿，尚未实现。依据：`inspector-ui/changes` 中 10 张参考图及其文件名观察。示例中的数据、按钮与交付流程不代表已经具备的 Git 写入能力。

## 定位与核心问题

Changes 帮助用户理解并控制即将交付的改动：在明确的比较范围内，连续审阅 diff，把问题定位到代码并交给 Agent 修正，选定提交内容，然后交付。核心链路为：看范围 → 看净变化 → 审阅 → 讨论/修正 → 确认提交内容 → 提交与 PR。

它应支持四类判断：

1. 我在比较什么仓库、工作树和版本？
2. 发生了什么净变化，哪些值得重点看？
3. 哪些内容已经审阅，审阅后是否又变了？
4. 下一次提交和 PR 会包含什么？

目标可以是逐步覆盖常用 Git 客户端的工作流。仅有漂亮的 diff 不能支撑替代：真正替代日常提交需要可靠的暂存、部分暂存、提交、推送、分支和冲突处理。重构历史、复杂合并等后续采用工作台中的专门流程，不把所有操作堆进文件行。

## 对参考设计的理解

- Session rail Changes 保留精简摘要和入口，不承担第二个完整变更列表。
- 主要阅读方式为连续的、可折叠的多文件 diff；搜索结果定位到文件的 diff，不是完整源码。
- 顶部比较标题同时表达 before 和 after；范围、比较基线和历史提交通过同一个入口选择。
- `Compare against` 在本方案中明确为改变比较基线，不 checkout 分支。截图没有证明该菜单会执行分支切换。
- 文件行中的圆圈勾，结合菜单 `Mark as viewed`，应设计成审阅标记，不作为暂存标记。
- 文件菜单包含附到上下文、复制、已查看、打开文件、外部打开、Finder 定位；未提供截图的其他菜单行为不推测为参考 App 的已实现规则。
- Commits 数字的具体统计范围不能从截图确定。我们的提交列表必须直接标注范围，不能只显示含义不明的数字。

## 一、范围与数据语义

用户设置的比较基线，与实际 checkout 分支、工作树身份分别保存和展示。

| 查看模式 | before → after | 用户要回答的问题 |
| --- | --- | --- |
| 全部改动 | 所选基线与 HEAD 的共同祖先 → 当前工作树 | 本分支从共同起点到当前状态的最终净变化 |
| 未提交改动 | HEAD → 当前工作树，另展示未跟踪文件 | 当前还没进入提交的内容 |
| 历史提交 | 所选提交的父版本 → 所选提交 | 这一次提交当时改了什么 |

“全部改动”不是逐次提交 diff 与未提交 diff 的相加，而是两个端点的净变化。未跟踪文件单独标识并纳入工作区呈现，不声称普通 Git diff 会自动包含它们。

未提交模式提供全部、已暂存、未暂存筛选：已暂存比较 HEAD 与 index，未暂存比较 index 与工作树；同一文件可以同时有两类差异。部分暂存必须可识别。

默认选择：有明确目标分支时使用该基线；否则优先仓库配置的默认分支，不硬编码 main。目标与当前分支相同，或没有适用的分支交付范围时，优先未提交模式。用户选择按 repository + worktree 记忆。无共同祖先、初始仓库、浅克隆缺少对象、detached HEAD、多重 merge base 均不能静默换成另一个范围；应明确说明并提供可用的模式/补充历史路径。多重 merge base 需要专门规则，首批不任意选择一个。

历史菜单显示当前分支的最近提交，支持搜索标题、SHA、作者。需要时可筛选“仅本次比较涉及的提交”，并显示这个范围。选择提交不 checkout；根提交对比空树，合并提交要明确选择的父版本，不能误称为普通单父提交。

依据：[git diff 官方文档](https://git-scm.com/docs/git-diff)、[git merge-base 官方文档](https://git-scm.com/docs/git-merge-base)。上述默认模式与文案是本产品提案，不是对参考 App 内部实现的断言。

## 二、UI 结构

### 外壳标题栏

只保留一行：比较标题及菜单、搜索、展开/收起、更多、完全显示、关闭。仓库/工作树身份必须可辨认，多仓库时提供轻量切换。比较菜单中显示当前实际分支；基线选择菜单明确标为“比较基线”。分支切换以后在独立入口中提供。

正文顶部用轻量摘要显示文件数、+/-、已查看进度和同步状态，不再增加一条常驻大导航栏。提交操作区在需要时展开，不挤占 diff 正文。

### 连续 diff

默认保持参考图的连续审阅：文件标题、对应 diff、下一个文件标题。初始展开，虚拟化和懒加载保证展开状态不等于立即计算所有 diff。

每个标题行包括：折叠按钮、图标、文件名、弱化父目录、明确的 A/M/D/R/冲突状态、+/-、已查看、打开文件和更多。小宽度时把次要动作收进更多，不依靠 hover 才能操作。文件名同名时显示足够的父路径区分；颜色配合文字和符号，不能仅靠红绿表达状态。

点击文件标题行展开/收起，勾选已查看或打开文件不触发展开状态。文件头随该文件内容滚动保持可定位的上下文；不使用多个文件头互相覆盖的层叠吸顶效果。

统一 diff 显示旧/新行号、整行 +/- 底色、行内变化强调、语法着色和可选择复制的文本。被折叠的未改动区域支持向上/下渐进展开或全部展开，不能首次加载整份大文件。源码长行在换行与横向滚动之间提供偏好；复制不带行号和 UI 符号。

文件行展开状态、阅读位置按比较范围保留。搜索按文件名和路径，选中后展开目标并跳到 diff；未查看筛选和下一个未查看提升大量文件审阅效率。

### 宽窄变化

- 窄面板仍采用单列连续 diff，点击文件不会切到一个空白目录占位，也不自动增宽或隐藏对话。
- 宽面板仍以 diff 为主体，可额外打开右侧改动文件大纲；不强制保留永久树栏。
- 只有用户点击完全显示才隐藏对话，Sidebar 按现有外壳规则保留。
- 宽度足够时可选左右对比；左右 diff 两边是版本内容，不是把文件列表算作其中一边。
- 收起全部时标题列表本身就是变更目录；搜索、快捷键和文件大纲共同承担快速跳转，不新增多级详情导航。

## 三、审阅状态

已查看不是已暂存，不表示自动审查通过，也不作为允许提交的强制门槛。进入视口、展开或停留不会自动标为已查看；用户明确操作后才记录。

审阅记录绑定仓库、工作树、比较端点和该文件差异的版本。Agent、编辑器或其他 Git 工具改变该文件后，仅该文件的对应标记失效，并提示有新改动；没有变化的文件保留记录。切换比较范围不继承另一套差异的标记。隐藏纯空白等显示选项时，要明确标记针对显示出来的内容还是完整 diff；首批建议按完整差异审阅，隐藏内容时保留提示。

用户正阅读或选择文本时，后台刷新先提示有更新，不抢滚动位置或替换正在选择的内容；重新加载后尽量以文件和 hunk 锚点恢复位置。历史提交 diff 保持固定，不随工作区更新变化。

## 四、对话与 Files 联通

选择一个或多个 diff 行/hunk，可以“附到对话”或“让 Agent 修改这处”。先形成未发送草稿：仓库/工作树、文件路径、before/after、位置和具体差异引用。用户写明意图后发送，不自动发送一整份仓库 diff。Agent 执行前如引用已过期，需要重新定位，不能盲用旧行号。

普通打开文件沿用已接通的 Files 单文件入口；删除行默认定位新版本邻近行，历史模式中明确区分“查看该版本文件”和“打开当前工作区文件”。只读历史内容不能进入当前文件的自动保存编辑器。

Git 总变化包含用户、Agent 和其他工具的修改。只有存在可靠的轮次/工具写入记录时才标识“本轮涉及文件”，它是来源线索，不能据此把整个文件当前差异都归给 Agent。没有证据时不展示“本次对话产生的全部改动”。

## 五、提交与交付

审阅默认界面保持克制；需要提交时进入未提交模式，展开暂存/提交区域。以真实 Git index 为准，提供文件级暂存和取消暂存，再逐步加入 hunk/行级暂存。比较基线的 All changes 中不直接对大范围差异做暂存或丢弃，避免把已提交内容误认为未提交内容。

提交前展示真实暂存区文件和变更数，部分暂存文件单独说明；提交说明可由 Agent 生成草稿，用户决定最终文本。若工作区/暂存区变动导致范围不再匹配，重新确认范围，不能提交 UI 中没展示的新内容。

Create PR 的实际流程为检查比较范围 → 处理需要纳入的未提交内容 → 确认推送 → 确认 PR。未提交内容不能直接当作远端 PR 内容。无远端、无托管平台能力、分支未推送或有冲突时，显示对应下一步而不是一个注定失败的按钮。首批没有写入能力时不展示假的可用提交/PR 按钮。

丢弃未提交修改、撤销一次提交、还原历史版本是不同动作，不能统一叫“撤销”。需要有范围预览与可恢复策略；冲突解决、分支切换、stash、合并、rebase、cherry-pick 在专门的仓库操作流程中逐步实现。

## 六、必须真实显示的状态

- 二进制文件显示类型/大小，图片在支持时提供前后预览；不能伪造 +/- 行数。
- 重命名显示旧路径 → 新路径，保留修改信息；不简单拆成新增与删除两项。
- 权限变化、符号链接、submodule、LFS 对象分别展示其元数据或能力限制。
- 冲突突出显示并提供入口，不作为普通红绿 diff 宣称已经解决。
- 无 Git 仓库、没有未提交改动、当前比较无差异是三个不同空状态。
- 大文件、截断、加载失败、权限问题、Git 不可用、缺失历史必须显示，不能呈现“干净工作区”。
- 仓库和工作树身份变动后，旧请求不可覆盖新视图；同一比较中的统计、列表、hunk、上下文应来自一致的快照。

## 七、现有能力与演进

目前本地 GitWorkingTreeReviewProvider 与 FileViewerKit FileReviewProvider 是 HEAD → 工作树的只读投影，界面主要是列表与选中 diff。code-agent 已有按 snapshot 读取的 Changes 概览/patch 接口。已完成 Changes 打开 Files。

仍缺比较基线/提交视图、完整 index 状态、版本关联的审阅记录、diff 到对话的精确引用以及 Git 写入流程。本批不改生产代码，不把这些能力视为现成。

后续保持 FileViewerKit 承担独立 diff 展示与交互；AgentKit 承担对话、审阅和交付状态；拥有仓库的 Runtime 承担 Git 数据和操作。Session rail、Changes 和提交检查使用同一数据范围，避免本机与服务端各算一套产生不同数字。按概览 → 按文件 patch → 按需上下文加载；不在窗口 resize、每个流式 token 或折叠操作时重跑 Git。

实施建议：

1. 审阅基础：连续 diff、搜索/展开、明确 HEAD 基线、状态完整性、版本化已查看与性能。
2. 比较与协作：目标分支、全部改动、历史提交、diff 引用到对话及版本定位。
3. 提交闭环：真实 index、文件/hunk 暂存、提交、推送和 PR。
4. 更完整的仓库管理：分支、stash、冲突解决、合并/变基等专门流程。

设计应覆盖完整闭环，实施按依赖推进。第 1、2 阶段产物是实用的审阅工作台；第 3 阶段完成后才具备替代常用 Git 客户端日常提交场景的基础。
